# v1.0.38 — the Google-Sheets sources list is gone

What changed, why, and what to delete after **2026-09-10**. Read this before touching
anything named `sunset`, `linksfile`, or `libraryId`.

## The problem

The sheet was a **second source of truth**. It was read on every sync, it **deleted** content
that disappeared from it (the presence mirror), and the app maintained a durable write-back
queue in the other direction. That shape is the direct cause of a long line of bugs —
v1.0.10, 1.0.12, 1.0.18, 1.0.19, 1.0.20, 1.0.26, 1.0.32, 1.0.34 all contain fixes whose root
was "two places disagreed". It was also a concept the parent this app is built for does not
have: they cannot mint a Google Cloud key, and by v1.0.32 list management had already been
taken out of their hands one control at a time.

## What replaced it

**The database is the only store.** The sources were always in it — `libraryChannels` rows are
the subscriptions, video records in the ⭐ folder are the individually added videos, and both
already travelled in the Drive document. So the model is now stated once:

> **the source of truth is (subscriptions, loose videos); everything else is derived.**

Measured: removing the sheet added **0 bytes** to the Drive document. (The separate question
of compacting that document — 614 → 175 bytes per record, 7 MB → 2 MB at the 12 000 cap — was
deliberately left out of this release: it is a one-way format change, and mixing it in would
have made a sync regression impossible to attribute.)

**Adding content**: the parent screen (paste a link / the built-in YouTube search), a share
from the YouTube app, and the new **links file**.

## The links file

The old sheet's row grammar, as a UTF-8 text file. One link per line, optionally
`link,name,auto|manual`, `#` is a comment. That choice is the whole trick: **no new parser and
no second safety boundary** — `parseCsv` → `parseSourceRows` → `classifySourceRow`. A CSV
pasted out of an old spreadsheet therefore imports unchanged.

Export writes **canonical links only** (`/channel/UC…`, `/playlist?list=…`, `/watch?v=…`, and
a direct file's original `srcUrl`). Never a YouTube video's stored `srcUrl`: it can carry
`?si=` tracking, an `m.youtube` host, a `?t=` seek — or a `&list=`, which reads back as a
PLAYLIST and imports hundreds of videos. Only `state === 'live'` travels, and only records no
subscription reproduces (`plan.coveredBySubscription`). Measured on a real library: **514
records → 4 lines, 551 bytes**.

Delivery is write-then-share, and every rung names where the file is. `'EXTERNAL'` is
permission-free; `DOCUMENTS` is not, and the manifest deliberately declares no storage
permission. The new native `shareFile` exists because `shareText` is `text/plain` +
`EXTRA_TEXT` and cannot attach a file.

Import has two doors — file picker and paste box — and **neither is the other's fallback**:
Android TV has no file picker at all. It does not route through `addClassifiedRow`: that
would be one approval dialog per channel and one forced sync per video.

## THE HOLE THIS RELEASE HAD TO CLOSE

A deletion tombstone was revocable by exactly one thing — **the sheet re-adding the key**
(`planSheetMirror.unDenyKeys`, v1.0.10) — and `drive.mergeDbFiles` deletes any video whose
tombstone is active from the merged document. So the moment the sheet went away, a parent who
deleted a video and later pasted it again would get it written, shown to the child, and
silently destroyed on the next pull, on every device.

**That hole was already open**: `addClassifiedRow` never consulted the deny set at all. The
sheet's un-deny was quietly repairing it. The replacement is an explicit parental answer
(`plan.deniedReAddPrompt`) — never automatic, because a parent who removed three bad videos
must not get them back for re-pasting a link (the v1.0.23 rule).

## Two more latent bugs the removal exposed

- **`planOrphanGC` never ran for a sheet-less profile.** It only ever ran inside
  `applySheetMirror`, gated on `if (sheetParsed)` — the normal case since v1.0.32 and the
  ONLY case now. So when a peer deleted a subscription, the v1.0.36 tombstone arrived, the row
  was deleted, and *nothing deleted the videos*: the child kept a folder full of a channel
  nobody subscribes to, forever. It is now an unconditional stage, with a new
  `orphanSweepValve` because the blast radius grew (`deleteVideoRaw` writes no tombstone, so a
  mass sweep churns against the Drive doc).
- **`profileSources` only carried an entry when a `sheetUrl` existed**, and the restore branch
  opened with `if (!ps.sheetUrl) continue`. After the migration that map is empty, so a fresh
  device restoring a migrated family got every record and **no sources row** — `ensureSources`
  mints `lib:p:<id>` while the content sits under the old `lib:<hash>`. Empty home, full
  database, and no repair tool (moveScope is deleted). The scope now travels explicitly.

## The migration (`sunset.js`) — ⏳ DELETE AFTER 2026-09-10

Per profile with a `sheetUrl`: read the sheet ONE last time → fold it into the database →
forget it (**`libraryId` UNTOUCHED**) → permanently delete the spreadsheet. Three read
attempts across launches, then it forgets anyway. Silent throughout.

It runs as a stage inside `app.entryRefresh`, **between the Drive pull and the sync**, awaited,
iterating `store.getProfiles()` itself. Not `dataver`: that runs before any profile is active,
blocks boot behind an already-faded splash with no progress UI, and means "run once" where
this needs "three attempts across launches".

The phase machine is pure `plan.planSheetSunset`, and the branch order IS the design:

| situation | why it must be that way |
|---|---|
| crash between FOLD and FORGET → resume at the forget, never re-read | in between, the parent may have deleted something in the app; a lingering sheet row must not undo it |
| crash between FORGET and DELETE → still delete, from the **snapshotted** id | after the forget there is no `sheetUrl` left to derive it from |
| no token → skip **without burning an attempt** | a family that never connected Google would exhaust three tries on launches that never reached the network |
| past the deadline → forget, no token needed, any attempt count | this is what makes the code deletable: no device can be left holding an inert `sheetUrl` |

**Two irrecoverable-loss guards.** (1) A sheet row carries no timestamp, and
`db.putLibraryChannel` stamps a fresh `updatedAt` that beats the v1.0.36 deletion tombstone by
design — so one last read would resurrect **every subscription the parent ever removed**.
`planSheetFold` skips any channel with a tombstone outright, and has **no revocation surface at
all** (`unDenyKeys` is deliberately not ported). (2) `interpretSheetResponse` keeps every
refusal, with its *reason* rewritten: there is no mirror left to mistake `[]` for "the parent
emptied the sheet", but a wrong `[]` now folds nothing, forgets the sheet, and then
**permanently deletes a file full of rows** — `files.delete` bypasses Drive's trash.

**The folder is never touched** — exactly one `files.delete`, on one spreadsheet id. Under
`drive.file` the app cannot see files the parent put in that folder, so it can never prove the
folder is empty, and deleting a Drive folder deletes its contents.

## What was deleted

`sheetwrite.js` (811 lines) · `sync.js` · the sheet stage and the presence mirror ·
`sync2.applySheetMirror` · `plan.planSheetMirror` / `sheetBackedKeysOf` /
`sourcesPanelActions` / `planScopeAdoption` · `db.moveScope` + `app.adoptLibraryScope` · the
whole sheet-setup wizard, its view and its nav registration · `#remote-connect` /
`#remote-copy` / `#sheetwrite-status` / the mirror valve UI · eleven sheet-write call sites ·
`sheetError` from the sync contract · six guide assets.
Renamed: `plan.isSheetBacked` → `isLooseRecord` (it never described a spreadsheet).
**The `'sheet'` FOLDER ID stays** — renaming it would be a `folderId` migration of every record
in every library and would break `pageAnyFolder` / `nextAfter` / `approvePending` / `snapshot` /
`share` at once.

Deleting `moveScope` / `planScopeAdoption` / `adoptLibraryScope` is what makes the sunset's
"`libraryId` never changes" rule **enforceable** rather than aspirational: no code path can
change a profile's scope any more.

**The complete list of things that may now delete a video record**: the parent's explicit 🗑️,
`db.purgeRejected`, the 30-day rejected expiry, the migration's `# הוסר` rows,
`db.purgeProfile`, and the orphan sweep. That list shrinking is the largest safety win here.

in that window reach only that device.
