# v1.0.25 — what changed, and why

Five features were requested. **Three of them already existed in the code and did not
work**, all for related reasons; one turned out to need no new behaviour at all; one is
genuinely new. This file is the record of the whole set. The enforcing detail for each
lives in [CLAUDE.md](../CLAUDE.md) — this is the map.

| # | Asked for | What it actually was | PR |
|---|---|---|---|
| 1 | Refresh after every add | **Existed since v1.0.21 and was broken by a race.** | [#41](https://github.com/devfassaf/kids_player/pull/41) |
| 4 | Ask what to do with a new channel | Existed for the parent screen; **the share path never had it.** | [#42](https://github.com/devfassaf/kids_player/pull/42) |
| 3 | Sync on every app entry | Both halves ran — **in parallel, which the docs forbade.** | [#43](https://github.com/devfassaf/kids_player/pull/43) |
| 2 | Sync parent settings | **Did not exist.** One setting travelled, by accident of where it lived. | [#44](https://github.com/devfassaf/kids_player/pull/44) |
| 5 | Continuous play | New. | [#45](https://github.com/devfassaf/kids_player/pull/45) |

---

## 1 · A forced sync joined the launch run

`syncLibrary` carried a comment saying *"A FORCED SYNC CHAINS, NEVER JOINS"* since v1.0.21
and shipped a condition that joined whenever the running sync was **also** forced. The
first sync of every launch is forced and takes minutes, so this collision was routine.

Adding a channel inside that window rode a run that had already listed the channels: it
finished "successfully", found 0 pending videos, **never showed the approval dialog**, and
reported `הערוץ סונכרן ✅` over an empty import. Pressing רענון נתונים fixed it — which is
exactly how it was reported from the field.

The same race silently reverted every `refreshAfterAdd` path to the v1.0.21 bug it exists
to prevent: no `srcChannelId` (the video sits in the loose list, not its channel folder)
and no `giftRank` (not a 🎁).

**Measured, not deduced.** In the live app the old code returned the *identical promise* to
the second forced caller and delivered it zero progress events — which is also why the
add-a-channel loading screen sat frozen. Decision core: pure `plan.planSyncDispatch`.

## 4 · A shared channel now asks the same question

The three-way dialog (`אישור הכל` / `אישור ידני` / `אחר כך`) existed for the parent screen.
`share.handleChannelShare` subscribed the channel, fired a sync it **did not await**, and
announced success immediately — so a shared channel's whole catalogue landed in ממתינים
with no dialog and no count. CLAUDE.md already claimed the question covered
*"parent screen + share"*; only one was true.

Both now go through `app.importChannelAndAsk`, and a test pins that it has **exactly two
callers**. The dialog itself needed no behavioural change — only the labels.

## 3 · The launch pull raced the launch sync

`nav.reset('gallery')` fires the gallery's `onEnter` **synchronously**, so the forced launch
sync was already running by the time `activateProfile` reached `pullThenSync` on the very
next line. Both write the same video records; CLAUDE.md has forbidden interleaving them
since v1.0.22. Every launch, every device with backup enabled.

One pipeline now (`entryRefresh`), one caller, one promise. A side effect is the feature as
asked: because the pull sits on the **home entry** rather than on activation, it also runs
on every later return home (throttled 60 s). Previously only a profile activation or a
resume ever pulled.

## 2 · Settings travel between devices

Before this, exactly one setting-like value crossed devices: `libraryChannels.autoApprove`,
and only because it rides a record that happens to carry a timestamp.

[`settings.js`](../www/js/settings.js) is the channel — `{account, profiles}`, per-key
last-write-wins, ties resolved the **safe** way. It lives in Preferences, not IndexedDB:
these are preferences, `pin.js` needs them before any database work, and it keeps the
channel testable in node.

Moved onto it: the **parent PIN** (account-wide), and per child the **exit lock**,
**share-approval** and **continuous play**.

Two things worth remembering:

- **The PIN migrates; the others do not.** "Start fresh" was the decision for the exit lock
  and share approval. A credential is different: with no PIN stored, `startPin` runs its
  SETUP flow, so the next person to reach the gate picks the new code — on a child's tablet,
  the child.
- **A per-profile lock opened a hole, closed in the same release.** The profile chip went
  straight to `backToProfiles`, so a child on a locked profile could tap their avatar, pick
  an unlocked sibling, and walk out. Two taps. Leaving a locked profile is now PIN-gated and
  **fails closed**, and `activateProfile` re-applies the lock on every switch.

## 5 · Continuous play

OFF by default, per child, synced. A family that never opens the settings screen keeps
v1.0.16 behaviour exactly.

Decision core: pure `playerlogic.planAutoplay` → `next | retry | stop`. `onExit` now carries
a reason, because `finish()` fires for broken videos too and a chain without that skips
through dead content in silence. One retry, then skip, then a five-failure ceiling — a
chain must always be able to end.

**Neither the 🎁 folder nor a 🎁 video is ever chained.** The folder rule was the agreed
one; the second half was found in the browser. Gift state lives per child *on the video*, so
wrapped tiles appear inside channel folders too — and the first tap on a gift unwraps it and
deliberately does **not** play. A chain calling `openWatch` would have skipped that ritual
and left the tile wrapped forever with its video already watched.

## Testing

**331 → 366 tests.** Every new guard in this release was **proven to fail on a planted
regression** before being kept — the repo has been bitten three times by guards that
pinned a fixture instead of the production path.

| Area | Where |
|---|---|
| `planSyncDispatch`, `planEntryRefresh`, `channelAddOutcome` | `test/plan.test.mjs` |
| `planAutoplay`, `nextInOrder`, timing relationships | `test/player.test.mjs` |
| settings storage + merge (commutative, idempotent) | `test/settings.test.mjs` |
| settings **on the wire** (serialize → parse → merge) | `test/gdrive.test.mjs` |
| PIN migration from an older install | `test/pin.test.mjs` |
| wiring pins — the tested core is the live one | `test/invariants.test.mjs` |

Two bugs in this release were caught by **browser verification, not by the suite**, and both
had green tests at the time:

1. **The PIN migration never ran.** `getSetting(scope, name, undefined)` triggers the
   `fallback = null` default, so "never written" read as "already migrated". Every unit test
   called `setPin()` first and therefore never took the lift branch. On a real install the
   parent gate would have opened for anyone.
2. **The chain would have opened wrapped gifts** (above).

Both now have their own tests.

## ⚠️ Upgrade notes

- **The exit lock and share-approval reset to their defaults.** A family running the kiosk
  will find it **off** after this update. This was a deliberate decision (2026-08-02); it
  must appear in the release notes.
- The parent PIN is preserved.
- Continuous play starts off, so nothing changes for anyone who does not turn it on.
